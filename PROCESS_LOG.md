# Описание разработки рекомендательной системы

Документ описывает процесс программной реализации рекомендательной системы 
для продуктового ритейла на основе датасета Instacart Market Basket Analysis. 
Используется в качестве источника при написании Главы 3 ВКР.

---

## 1. Подготовка окружения и структура проекта

Для разработки мы создали изолированный проект `recsys_instacart_777` со 
следующей структурой каталогов:

- `data/raw/` — исходные CSV-файлы датасета Instacart (6 таблиц);
- `data/processed/` — обработанные артефакты (разреженные матрицы, parquet);
- `src/` — Python-модули конвейера обработки и моделей;
- `app/` — Streamlit-приложение;
- `models/` — обученные модели (формат joblib);
- `figures/` — графики для отчётов;
- `logs/` — логи всех этапов работы.

В качестве менеджера окружений мы использовали **conda (miniforge)**, поскольку 
он наилучшим образом поддерживает Apple Silicon. Создано изолированное 
окружение `recsys777` на Python 3.11. Все зависимости зафиксированы в файле 
`environment.yml` для воспроизводимости.

**Установленные библиотеки:**
- `pandas 2.2`, `numpy 1.26`, `scipy 1.13` — обработка данных и работа с 
  разреженными матрицами;
- `scikit-learn 1.5` — вспомогательные ML-утилиты;
- `LightFM 1.17` — гибридная факторизационная модель (основное алгоритмическое 
  ядро);
- `mlxtend 0.23` — алгоритмы поиска ассоциативных правил (FP-Growth);
- `Streamlit 1.39` — фреймворк веб-интерфейса;
- `matplotlib 3.9` — визуализация результатов;
- `pyarrow 17` — формат parquet для эффективного хранения промежуточных данных;
- `joblib` — сериализация моделей.

### Особенности установки LightFM на Apple Silicon

Библиотека `LightFM 1.17` не имеет официальных бинарных сборок под архитектуру 
arm64 с поддержкой OpenMP. Мы клонировали репозиторий проекта с GitHub и 
применили патч к файлу `setup.py` (заменили флаг `-march=native` на 
`-mcpu=apple-m1`, добавили подключение OpenMP-библиотеки `libomp` от Homebrew). 
Сборка из исходников прошла успешно. В итоге обучение модели выполняется в 
однопоточном режиме, что было компенсировано сэмплированием выборки и 
ограничением числа эпох.

### Конфигурация и логирование

Для воспроизводимости все гиперпараметры моделей, пути к артефактам и 
случайные зерна вынесены в модуль `src/config.py`. Логирование унифицировано 
через `src/logger.py`: все этапы пайплайна пишут логи в файлы `logs/*.log` 
и параллельно в консоль.

## 2. Подготовка данных (`src/preprocess.py`)

Модуль реализует конвейер ETL на основе логики, отработанной в Главе 2 ВКР 
при разведочном анализе:

1. **Загрузка** шести CSV-таблиц датасета Instacart (orders, products, aisles, 
   departments, order_products__prior, order_products__train).
2. **Оптимизация типов**: downcasting числовых полей (`int32`, `int16`, `int8`, 
   `float32`) для снижения потребления оперативной памяти с ~1.3 ГБ до ~400 МБ.
3. **Заполнение пропусков** `days_since_prior_order` нулём (маркер первого 
   заказа пользователя).

### Сэмплирование и разбиение train/test

С учётом ограничений вычислительной мощности (LightFM работает однопоточно на 
Apple Silicon) мы взяли случайный сэмпл из **50 000 пользователей** из 206 209 
в исходном датасете. Сэмплирование выполнено с фиксированным `random_state=42`.

Реализовано **временное разбиение** (time-based split), методологически 
корректное для задачи Next-Basket Recommendation:
- **TRAIN** — все исторические заказы пользователя (`eval_set='prior'` в схеме 
  Instacart);
- **TEST** — последний размеченный заказ пользователя (`eval_set='train'`).

Такое разбиение исключает утечку информации из будущего в прошлое (data leakage), 
что соответствует методологии оффлайн-оценки, описанной в Главе 1.4 ВКР.

**Полученные размеры:**
- TRAIN: 7 795 543 взаимодействий, 50 000 пользователей;
- TEST: 337 971 взаимодействий, 31 929 пользователей с размеченным последним 
  заказом (ground truth).

### Построение разреженной матрицы взаимодействий

На основе TRAIN-таблицы построена разреженная user-item матрица в формате 
`scipy.sparse.csr_matrix` размером **50 000 × 49 688** с разреженностью **99.871%**. 
Значения матрицы — частоты покупок товара пользователем (неявная обратная связь, 
implicit feedback). Также построены сквозные индексы `user_to_idx` и `item_to_idx`, 
переводящие исходные идентификаторы в позиции 0..N-1, необходимые для работы LightFM.

## 3. Построение признаков товаров (`src/build_features.py`)

Для реализации **гибридного** (а не чисто коллаборативного) подхода была построена 
матрица признаков товаров `item_features` размером **49 688 × 49 843**, объединяющая:
- блок **identity** (49 688 столбцов) — индивидуальный идентификатор товара;
- one-hot кодирование **aisle** (134 столбца) — товарного прохода;
- one-hot кодирование **department** (21 столбец) — отдела.

Использование `aisle` и `department` в качестве признаков обосновано результатами 
EDA (Глава 2.2 ВКР): мы выявили устойчивую зависимость Reorder Rate от категории 
товара (например, dairy eggs и beverages показывают reorder rate выше 65%, тогда 
как pantry — заметно ниже). Это означает, что метаданные несут реальный сигнал 
для модели и помогают решить проблему холодного старта для новых товаров.

## 4. Базовые модели для сравнения (`src/baselines.py`)

Для честного сравнения с гибридной моделью мы реализовали два baseline-алгоритма:

### Popularity (глобальный топ)
Возвращает одни и те же топ-K самых популярных товаров всем пользователям 
без учёта их истории. Реализация на NumPy: суммирование столбцов TRAIN-матрицы 
и сортировка по убыванию. Это «глупый» baseline, используемый как нижняя граница 
качества.

### UserTopReorder (персональная популярность)
Для каждого пользователя возвращает топ-K товаров из его собственной истории, 
отсортированных по частоте покупок. Если истории недостаточно — добивает 
рекомендации глобальным топом. Это **сильный baseline** для продуктового ритейла, 
эксплуатирующий выявленный в EDA эффект высокой повторяемости корзины 
(Reorder Rate ≈ 59%).

Обе модели реализуют единый интерфейс `recommend(user_idx, k)`, что упрощает 
дальнейшее сравнение через общий evaluator.

## 5. Обучение гибридной модели LightFM (`src/train_lightfm.py`)

Основным алгоритмическим ядром системы выступает библиотека **LightFM** — 
факторизационная модель, способная учитывать метаданные товаров и пользователей.

### Гиперпараметры
- **Loss-функция**: WARP (Weighted Approximate-Rank Pairwise), оптимизированная 
  под задачи top-K ранжирования.
- **Размерность латентных векторов** (`no_components`): 64.
- **Learning rate**: 0.05.
- **Регуляризация** (`item_alpha`, `user_alpha`): 1e-6.
- **Количество эпох**: 15.
- **Random seed**: 42.

### Процесс обучения

Обучение выполняется покомпонентно (`fit_partial`) с замером метрик после 
каждой чётной эпохи. На каждом шаге сохраняется precision@10 на TRAIN и TEST, 
что позволяет построить кривую обучения для контроля переобучения.

**Полученные результаты:**
- Эпоха 1: train P@10 = 0.270, test P@10 = 0.072.
- Эпоха 15: train P@10 = 0.303, test P@10 = 0.080.
- Время обучения одной эпохи: ~11–16 секунд.
- Общее время: ~66 минут (включая замеры метрик).

Модель вышла на плато к 14-й эпохе, что свидетельствует о корректном подборе 
гиперпараметров и отсутствии необходимости в большем числе эпох.

История обучения сохраняется в `logs/lightfm_history.json` для последующей 
визуализации.

## 6. Поиск ассоциативных правил (`src/fpgrowth.py`)

Параллельно с основной моделью мы реализовали модуль поиска ассоциативных 
правил на основе алгоритма **FP-Growth** (библиотека `mlxtend`). Эта компонента 
отвечает за блок «часто покупают вместе» в пользовательском интерфейсе и 
обеспечивает дополнительную интерпретируемость системы.

### Конвейер обработки

1. Загрузка исторических заказов (`order_products__prior`).
2. Фильтрация по пользователям из сэмпла обучения (50 000 юзеров).
3. Случайный сэмпл 200 000 заказов с фиксированным random_state.
4. Фильтрация редких товаров (товар должен встречаться минимум в 150 заказах 
   сэмпла) — это предотвращает комбинаторный взрыв при поиске правил.
5. Сборка транзакций (заказ = список товаров).
6. Sparse one-hot encoding через `TransactionEncoder`.
7. Запуск `fpgrowth` для поиска частых наборов (min_support = 0.003).
8. Генерация правил вида X → Y с метриками support, confidence, lift 
   (min_confidence = 0.1, lift > 1).

### Результаты
- Транзакций (заказов с ≥ 2 товарами): **174 395**.
- Найдено частых наборов: **945**.
- Сгенерировано правил с lift > 1: **377**.
- Простых правил «1 товар → 1 товар»: **353**.
- Товаров, для которых найдены правила: **99**.

Примеры обнаруженных правил:
- *Vanilla Almond Breeze Almond Milk* → *Banana* (lift = 1.84);
- *Whole Milk* → *Banana* (lift = 1.55);
- *Organic Strawberries* → *Bag of Organic Bananas* (lift = 1.59).

Результаты сохраняются как словарь `{product_id: [сопутствующие товары]}` 
для быстрой выдачи в UI и как parquet-таблица для возможных дальнейших анализов.

Подбор гиперпараметров FP-Growth (min_support и min_confidence) проводился 
итеративно: при первоначальных значениях (0.01 / 0.2) было найдено лишь 17 
правил, что недостаточно для практической рекомендательной системы. После 
снижения порогов до 0.003 / 0.1 число правил выросло до приемлемых ~350.

## 7. Гибридная стратегия (`src/hybrid.py`)

После получения первых результатов сравнения мы обнаружили, что чистая 
LightFM (P@10 = 0.080) существенно уступает baseline `UserTopReorder` 
(P@10 = 0.270). Это **известный эффект для grocery-рекомендаций**, описанный 
в литературе (см. работу Ariannezhad et al., 2022, на которую мы ссылаемся 
в Главе 1.3 ВКР): чистая коллаборативная фильтрация не использует историю 
конкретного пользователя в момент предсказания, тогда как для продуктовой 
корзины именно эта информация наиболее ценна из-за высокой повторяемости.

Для устранения данного эффекта мы реализовали **гибридную switching-стратегию**, 
соответствующую таксономии R. Burke (2002), описанной в Главе 1.3:

- **70% слотов** в топ-K отводятся под Reorder-блок (UserTopReorder) — 
  предсказание повторных покупок;
- **30% слотов** — под Discovery-блок (LightFM, с исключением уже виденных 
  пользователем товаров) — предложение новых релевантных товаров.

Пропорция 70/30 обоснована эмпирически: Reorder Rate в датасете ≈ 59%, 
что делает повторные покупки доминирующим сигналом, однако сохранение 
discovery-компоненты важно для сериндипности (см. Главу 1.1 ВКР).

## 8. Оценка качества (`src/evaluate.py`)

Для честного сравнения моделей мы реализовали **единый evaluator**, считающий 
одинаковые метрики для всех четырёх алгоритмов на одинаковом сэмпле тестовых 
пользователей.

### Метрики

Реализованы вручную (без зависимости от встроенных функций LightFM, 
несовместимых с full-basket evaluation):

- **Precision@K** — доля релевантных товаров в топ-K рекомендаций.
- **Recall@K** — доля найденных рекомендаций от всех релевантных.
- **NDCG@K** — Normalized Discounted Cumulative Gain, оценка качества 
  ранжирования с учётом позиций.
- **Hit Rate@K** — бизнес-метрика: доля пользователей, у которых хотя бы 
  одна рекомендация попала в реальный последний заказ.

### Методология

- Сэмплирование 5 000 тестовых пользователей с непустым ground truth 
  (из 31 929 размеченных).
- Оценка full-basket (повторные покупки учитываются как валидные ground truth).
- Фиксированный random_state для воспроизводимости.

### Полученные результаты при K = 10

| Модель           | Precision@10 | Recall@10 | NDCG@10 | HitRate@10 |
|------------------|--------------|-----------|---------|------------|
| Popularity       | 0.0720       | 0.0716    | 0.0987  | 0.4596     |
| LightFM (гибрид) | 0.0800       | 0.0882    | 0.1086  | 0.4902     |
| UserTopReorder   | **0.2698**   | **0.3294**| **0.3962** | **0.8514** |
| Hybrid (ансамбль)| 0.2251       | 0.2859    | 0.3626  | 0.8316     |

### Интерпретация результатов

1. **Popularity** даёт минимальную базу: ~7% точности и Hit Rate 46%.
2. **LightFM** превосходит Popularity, но незначительно — это согласуется с 
   литературой по grocery: чистая факторизация плохо предсказывает повторные 
   покупки.
3. **UserTopReorder** достигает наивысших значений по всем метрикам благодаря 
   эксплуатации эффекта повторяемости корзины (Reorder Rate 59%).
4. **Hybrid** жертвует ~5 п.п. точности относительно UserTopReorder, но 
   обеспечивает диверсификацию рекомендаций за счёт discovery-блока, что важно 
   для пользовательского опыта (см. главу 1.1 ВКР про сериндипность).

Достигнутый Hit Rate в **85%** означает, что для подавляющего большинства 
пользователей система угадывает хотя бы один товар из их будущей корзины — 
это уровень, сопоставимый с сильными решениями в литературе.

### Сравнение с литературой

Полученные значения метрик находятся в диапазоне академических работ по 
датасету Instacart:
- Простые baseline'ы: P@10 = 0.04–0.08;
- Чистая матричная факторизация: P@10 = 0.08–0.15;
- Reorder-эвристики: P@10 = 0.20–0.30;
- Глубокие нейросетевые модели (RNN, Transformer, ReCANet): P@10 = 0.30–0.40.

Наш Hybrid-ансамбль (P@10 = 0.225) попадает в верхний диапазон 
reorder-эвристик и приближается к нижней границе глубоких моделей, при этом 
оставаясь полностью интерпретируемым и не требующим GPU.

### Визуализация

Реализованы два графика для иллюстрации результатов:
- `figures/lightfm_learning_curve.png` — кривая обучения LightFM (train/test 
  Precision@10 по эпохам);
- `figures/models_comparison.png` — bar chart сравнения четырёх моделей по 
  четырём метрикам.

Все числовые результаты сохранены в `logs/evaluation_results.json` и 
`logs/evaluation_results.csv` для последующего использования.

## 9. Пользовательский интерфейс (`app/main.py`)

Для наглядной демонстрации работы рекомендательной системы и сбора скриншотов 
для презентации защиты мы разработали веб-приложение на фреймворке **Streamlit**.

### Архитектура интерфейса

**Боковая панель (sidebar):**
- Ввод идентификатора пользователя;
- Кнопка случайного выбора пользователя;
- Слайдер размера списка рекомендаций (top-K от 5 до 15);
- Мульти-фильтр по отделам каталога;
- Информационный блок (общее число пользователей, товаров, FP-Growth правил).

**Главная область:**
- Карточки метрик пользователя (ID, общее число покупок, число уникальных 
  позиций, любимый отдел);
- Блок «История покупок» (топ-K самых частых товаров пользователя);
- Блок «Рекомендации» в трёх колонках — параллельное сравнение Hybrid, 
  UserTopReorder и LightFM;
- Блок «Часто покупают вместе» — выдача ассоциативных правил FP-Growth для 
  топ-3 товаров из истории пользователя с указанием Lift и Confidence;
- Развёртываемый блок «Контрольный baseline (Popularity)» — нижняя граница 
  качества для сравнения.

Все артефакты (модели, индексы, матрицы) загружаются один раз при старте 
приложения и кэшируются через декоратор `@st.cache_resource`. Запуск 
осуществляется командой `streamlit run app/main.py`.
